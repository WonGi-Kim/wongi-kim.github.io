01회원마다 반복하던 조회를, 한 번에 모아서.배치 조회 · ID 기반 Map · DTO 조립+

문제

회원 목록을 만드는 동안 지점·등록 프로그램·회기·담당 치료사를 반복 조회했습니다. DTO를 조립하는 단계까지 데이터 접근이 이어져, 목록을 조회하는 비용이 커졌습니다.

선택

현재 페이지의 회원 ID를 모아 연관 정보를 배치 조회했습니다. ID를 키로 하는 HashMap과 그룹 Map으로 데이터를 연결하고, 순회 순서를 유지해야 하는 곳은 LinkedHashMap을 사용했습니다. DTO에는 이미 조회한 데이터를 전달하도록 바꿨습니다.

결과

일반 회원 249 → 67ms
담당 회원 2,220 → 234ms

02결제 채널은 연결하고, 환불 조건은 명확하게.NICEPAY · 사용량 기반 환불 · 결제권 이력+

문제

온라인·링크·단말 결제는 응답 형식이 다릅니다. 환불은 회기 진행량, 피드백, 대면 여부와 쿠폰 사용에 따라 계산 기준이 달라지고, 환불 이후의 이용 권한에도 영향을 줍니다.

선택

여러 결제 채널을 내부 결제 모델로 연결하고, 채널별 상세 데이터는 JSON으로 관리했습니다. 실결제·쿠폰 금액을 상품 기준에 따라 안분하고, 일반·연장 결제권 이력과 사용량 기반 환불 계산을 연결했습니다.

결과

승인·취소와 예상 환불 금액 조회, 환불 후 남은 결제권과 이용 권한을 함께 처리하는 흐름을 구현했습니다. 정산은 MySQL JSON 함수와 Native Query로 DB에서 추출·집계하도록 구성했습니다.

03예약이 바뀌어도, 회기의 연결은 이어지도록.Session Shifting · 트랜잭션 · 중복 제출 방어+

문제

예약 취소는 이후 회기의 순서와 예약 매핑에도 영향을 줍니다. 워크북 제출이 동시에 들어오면 최초 제출에 따른 후처리와 알림이 중복 실행될 수 있었습니다.

선택

예약 취소 시 이후 회기와 예약의 연결을 재구성하는 Session Shifting을 구현하고, 관련 데이터를 한 트랜잭션에서 갱신했습니다. 워크북 제출에는 DB 행 잠금과 기존 완료 상태 확인을 적용했습니다.

결과

회기 재배치를 자동화하고, 최초 제출 여부에 따라 완료 처리와 알림 발송을 분기해 중복 처리를 방어했습니다.

04파일과 데이터의 변경 순서까지 설계하기.Presigned URL · 커밋 후 정리 · 공통 로깅+

파일

NCP Object Storage와 Presigned URL로 직접 업로드를 구현했습니다. 파일 교체 시 DB 커밋 이후 기존 객체를 삭제하도록 순서를 정리해, DB 변경 실패에도 기존 파일을 유지할 수 있도록 했습니다.

운영

Spring AOP로 Service·Repository 실행시간과 예외를 공통 기록했습니다. 익명 사용자 처리에서 발생하던 불필요한 오류와 중복 로그를 줄이고, 서버 오류의 추적 정보는 유지했습니다.

검증

척도 검사 8종의 응답 인덱스·점수 변환과 입력 검증을 정리했습니다. 인증·로그 변경은 JUnit, Mockito, MockMvc로 회귀 검증했습니다.
